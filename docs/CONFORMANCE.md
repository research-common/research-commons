# Conformance cases for the claims model

**Status:** proposed, open for review alongside the design note. Companion to `DESIGN-notes-claims-model.md`.

This document turns the design note *Invariants and the claims model* (#69) into observable, testable
obligations. It is the test plan for the implementation of that note and the artifact a second implementation
claims conformance against. Every case names the note section or invariant it pins, so the note stays
authoritative: when a case and the note disagree, the note wins and the case is wrong. Cases describe what a
test constructs and what it must observe; they do not describe how an implementation is built. Nothing here is
claimed as implemented or run.

## How a result is recorded

A conformance result is only as good as its record. For each case an implementation reports:

- **the code revision** under test, and the **versions of the core and each profile** it claims;
- **digests of every fixture** (blobs, statements, keys, block evidence) the case consumed, so the run is
  reproducible byte for byte;
- **the policy digest**: the exact trust, admission, execution and reference policy the reader held;
- **the evaluator context**: evaluator version and the time the reader used, since several answers (shelf life,
  finality, future-timestamp refusal) depend on it;
- **the exact invocation**: the command or API call as issued, with every argument;
- **typed expected and actual results**: the state token, exit code, displayed value or refusal class and scope
  that the case requires, next to what was observed, in the same vocabulary as §13 of the note.

Tests use **disposable keys** generated for the run and **throwaway roots**; no case touches a live hub or a key
that signs anything outside the test.

A **negative test must show that its mutation reached the boundary it is testing**. A refusal for the wrong
reason (a size limit tripped before the signature check ran, a parser error before the policy gate) is not a
pass. Each negative case therefore says how the test proves delivery: the parsed digest is logged, the
evaluator names the rule it loaded, a canary outside the boundary is checked, a process audit records what was
spawned.

Unit and property tests suit pure folds (resolution, grouping, credit); real-signature integration tests suit
authentication; two-root end-to-end tests suit admission; fault injection suits durability; shared vectors suit
serialization once the wire-format note exists. Mocks are fine, but a mocked layer establishes nothing about
the layer it replaces.

## Core and profiles

The note's obligations divide into a **core** (statements, identity, resolution, resources, hubs and gates,
outputs) and three profiles:

- **execution**: the sandbox and `run` (§12 and the `run --publish` path);
- **exchange**: tasks, settlement, quorums, pre-registration and credit (§9);
- **bitcoin-time**: Bitcoin-quality time evidence verified by the reader (§10, #59).

An implementation declares which of the four it supports and, for each, **lists by id every case it does not
pass or does not implement**. There is no blanket conformance claim: "conforms to core" without a case list is
not a conformance statement. A case tagged to a profile the implementation does not declare is reported as
`unsupported`, not omitted.

A fifth scope, **discovery** (hub conventions, #66), has no cases yet. The note defers hub conventions to a
separate note and states no testable obligation for them.

Case ids are `C-core-nn`, `C-exec-nn`, `C-exch-nn`, `C-btc-nn`, and `P-nn` for properties that quantify over
generated inputs. Within a table, cases are ordered by note section. The `note` column names the invariants and
sections that state the obligation. Open items at the end record where drafting found the note silent and the
amendment that answered it.

Conventions used in scenarios: `A`, `B`, `C`, `O1`, `O2` are disposable keys; "permute" means the test replays
the same statement set in every delivery order and with duplicates and asserts the answer is unchanged (I14);
"bitcoin-verified" means the test supplies block evidence the reader is configured to trust, so the reader
itself verifies the proof (§10); "local" means a signed, self-consistent anchor with no such evidence. Exit codes
refer to `verify` unless another command is named (§13).
